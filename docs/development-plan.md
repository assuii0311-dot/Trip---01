# 여행 계획 프로그램 개발 계획

## 1. 개요

여행 계획 프로그램을 개발하기 위한 단계별 계획이다.
각 단계의 목적, 주요 활동, 산출물, 완료 기준을 정의한다.

관련 문서: 요구사항 `docs/01-requirements.md`, 결정 기록 `docs/decisions.md`, 과업 리스트 `docs/TASKS.md`, 엔진 설계 `docs/engines/`.

### 전제 조건

- 유료 데이터는 사용하지 않는다. 무료 티어만 제공하는 유료 서비스도 사용량 증가 시 과금되므로 제외한다. 외부 서비스로 이동하는 링크 제공은 유료 데이터 이용에 해당하지 않는다(D-013).
- 서버 비용은 쓰지 않는다. 앱은 GitHub Pages로 제공하고 데이터는 여행별 GitHub 저장소에 둔다(D-011).
- 개발 과정에서 클로드(Claude)를 활용한다. 따라서 각 단계의 산출물은 저장소 안에 문서 파일로 남겨 이후 단계의 참조 자료로 사용한다.
- 대상 플랫폼과 기술 스택은 아직 정하지 않았다. 5단계 기술 설계에서 결정한다. 단, D-011에 따라 웹에서 동작하는 형태로 좁혀졌고 개발 기기는 아이패드다.

### 진행 원칙

- 각 단계는 산출물이 저장소에 커밋되고 완료 기준을 충족했을 때 종료한다.
- 2단계 데이터 조사 결과에 따라 1단계 요구사항을 다시 조정할 수 있다. 1단계와 2단계는 한 방향이 아니라 피드백 루프다.
- 6단계 개발은 전체를 한 번에 만들지 않고 MVP 기능 단위로 구현, 테스트, 검증을 반복한다.
- 4단계 디자인은 정적 시안에서 끝내지 않고 간단한 코드 프로토타입으로 검증한다.
- 데이터 제약이 있는 기능은 제외하지 않고 확보 가능한 데이터 수준에 따른 대안 사다리로 다룬다. PoC는 모든 항목을 시도하고 결과를 추출 가능, 불확실, 추출 불가로 분류한다(D-013).
- 별도 설계가 필요한 구성 요소는 엔진으로 분리해 `docs/engines/`에 설계 문서를 두고, 구현은 설계 문서 동의 후 착수한다(D-012).

## 2. 단계별 계획

### 1단계. 요구사항 정의

- 목적: 무엇을, 왜, 누구를 위해 만드는지 정의한다.
- 주요 활동
  - 해결하려는 문제와 대상 사용자 정의
  - 핵심 기능 목록과 우선순위 정리
  - 비기능 요구사항 정리 (오프라인 동작 여부, 성능, 언어 등)
  - 이번 개발의 범위와 범위 밖 항목 명시
- 산출물: `docs/01-requirements.md` (제품 요구사항 문서)
- 완료 기준: 핵심 기능 목록에 우선순위가 매겨져 있고, 범위 밖 항목이 명시되어 있다.

### 2단계. 활용 가능한 데이터 정의

- 목적: 유료 데이터 없이 어떤 데이터를 어디서 확보할 수 있는지 확정한다.
- 주요 활동
  - 후보 데이터 소스 조사 (공공데이터 API, OpenStreetMap 계열, 기상 API, Wikidata 등)
  - 완전 무료 소스와 무료 티어만 있는 유료 서비스 구분
  - 라이선스와 이용약관 확인 (상업적 이용 가능 여부, 출처 표기 의무, 재배포 가능 여부)
  - 제약 조건 확인 (일일 호출 한도, 갱신 주기, 국내외 커버리지, 데이터 품질)
  - 실제 호출 스크립트로 응답 형식과 품질 검증 (PoC). 확인 항목은 요구사항 정의서 12절(P-01 ~ P-16)을 따른다
  - PoC 결과를 항목별로 추출 가능, 불확실, 추출 불가로 분류하고 대안 사다리의 단계 확정 (D-013)
  - 데이터가 없는 영역의 대안 정의 (자체 큐레이션, 캐싱, 외부 링크 등)
  - E1 데이터 수집·정규화, E3 이동 시간, E6 비용 추정 엔진의 PoC와 설계 병행 (T-011, T-013, T-016)
  - 조사 결과를 바탕으로 1단계 요구사항의 입력 항목과 조건부 기능 재조정
- 산출물
  - `docs/02-data-sources.md` (데이터 소스 비교표, 라이선스, 제약 조건)
  - `docs/02-data-model.md` (데이터 모델 초안)
  - PoC 결과 분류표 (항목별 추출 가능, 불확실, 추출 불가): `docs/02-poc-classification.md`
  - PoC 스크립트
  - `docs/engines/` E1, E3, E6 설계 문서 초안
- 완료 기준: 요구사항 정의서의 데이터 의존 기능 각각에 대해 데이터 소스가 확정되었거나 대안 사다리의 단계가 확정되었다. PoC 분류표가 작성되었고 그 결과로 요구사항 정의서가 재조정되었다.
- 후속 조치: 2단계 완료 직후 작업 분해 기반 일정 추정(T-009)을 수행해 11월 완료 가능 여부를 판단한다(D-014).

### 3단계. 기획

- 목적: 요구사항과 데이터를 바탕으로 어떤 기능과 화면 흐름으로 만들지 정한다.
- 주요 활동
  - 기능 명세 작성 (기능별 입력, 처리, 출력)
  - 정보 구조와 화면 흐름 정의
  - MVP 범위 확정 (첫 반복에서 만들 기능)
  - 엔진 설계 문서 작성: E2 추천, E4 일정 생성, E5 장소 설명 생성, E7 동기화 (T-012, T-014, T-015, T-017). 2단계에서 시작한 E1, E3, E6 설계 문서 확정
- 산출물
  - `docs/03-feature-spec.md` (기능 명세)
  - `docs/03-screen-flow.md` (화면 흐름)
  - `docs/03-mvp-scope.md` (MVP 범위)
  - `docs/engines/` E1 ~ E7 설계 문서
- 완료 기준: MVP에 포함되는 기능과 화면이 목록으로 확정되어 있고, 엔진 7개의 설계 문서가 모두 "설계 동의" 상태다.

### 4단계. UI/UX 디자인

- 목적: 화면 구성과 사용자 경험을 확정한다.
- 주요 활동
  - 화면별 와이어프레임 작성
  - 공통 컴포넌트와 스타일 규칙 정의
  - 간단한 코드 프로토타입으로 흐름 검증
- 산출물
  - `docs/04-wireframes.md` (와이어프레임과 화면 설명)
  - `docs/04-design-rules.md` (스타일 규칙)
  - 프로토타입 코드
- 완료 기준: MVP 범위의 모든 화면에 와이어프레임이 있고, 프로토타입으로 주요 흐름이 검증되었다.

### 5단계. 기술 설계

- 목적: 플랫폼, 기술 스택, 아키텍처를 결정한다.
- 주요 활동
  - 대상 플랫폼 결정 (iOS, Android, 크로스플랫폼, 웹). 제약: D-011에 따라 앱은 GitHub Pages로 제공하므로 웹에서 동작하는 형태여야 하고, 개발 기기는 아이패드다
  - 기술 스택 결정
  - 아키텍처와 모듈 구조 정의. 엔진별 독립 모듈과 자체 테스트 구조 포함 (D-012)
  - GitHub Pages 앱 저장소와 여행별 데이터 저장소 구조, Key 동기화와 암호화 설계 반영 (D-011)
  - 외부 데이터 호출 계층 설계 (무료 API 호출 한도 대응을 위한 캐싱 전략, 장애 시 폴백)
  - 데이터 모델 확정
  - 테스트 전략 정의
- 산출물
  - `docs/05-architecture.md` (플랫폼, 스택, 아키텍처, 캐싱과 폴백 전략)
  - `CLAUDE.md` (프로젝트 규칙과 기술 스택, 클로드 참조용)
- 완료 기준: 기술 스택이 확정되었고, 외부 데이터 호출 한도를 넘지 않는 캐싱 전략이 문서화되었다.

### 6단계. 개발

- 목적: MVP를 구현한다.
- 주요 활동
  - MVP 기능 단위로 구현, 자동화 테스트 작성, 검증을 반복
  - 엔진은 설계 문서가 "설계 동의" 상태일 때만 구현에 착수 (D-012)
  - 각 반복이 끝날 때마다 커밋
  - 반복마다 기능 명세와 실제 구현의 차이를 문서에 반영
- 산출물: 동작하는 MVP 코드와 자동화 테스트
- 완료 기준: MVP 범위의 모든 기능이 구현되었고 자동화 테스트가 통과한다.

### 7단계. 테스트 및 배포

- 목적: 실제 사용 환경에서 검증하고 배포한다.
- 주요 활동
  - 실기기 테스트
  - 베타 테스트와 피드백 수집
  - 스토어 등록 준비 (대상 플랫폼에 따라 결정)
- 산출물
  - `docs/07-test-report.md` (테스트 결과)
  - 배포 가능한 빌드
- 완료 기준: 베타 테스트에서 발견된 치명적 문제가 해결되었고, 배포 절차가 문서화되었다.

### 8단계. 운영 및 피드백 반영

- 목적: 사용자 피드백을 수집하고 다음 반복 계획을 세운다.
- 주요 활동
  - 사용자 피드백과 오류 수집
  - 데이터 소스 변경 여부 점검 (API 정책 변경, 서비스 종료 등)
  - 다음 반복에서 다룰 기능 선정
- 산출물: `docs/08-feedback-log.md` (피드백과 다음 반복 계획)
- 완료 기준: 다음 반복의 범위가 정해져 3단계 기획으로 돌아간다.

## 3. 단계 간 관계

```
1단계 요구사항 정의
   ↕ (데이터 가용성에 따라 요구사항 재조정)
2단계 데이터 정의 ── E1, E3, E6 엔진 PoC와 설계 병행
   ↓ (작업 분해 기반 일정 추정, T-009)
3단계 기획 ── E2, E4, E5, E7 엔진 설계, E1, E3, E6 설계 확정
   ↓
4단계 UI/UX 디자인
   ↓
5단계 기술 설계
   ↓
6단계 개발 (MVP 기능 단위 반복)
   ↓
7단계 테스트 및 배포
   ↓
8단계 운영 및 피드백 → 3단계로 복귀
```

# E7. 동기화 엔진

- 상태: 설계 동의 (2026-10-25, D-025)
- 관련 요구사항: R-09, R-21, R-22, R-23, R-24, R-25
- 관련 결정: D-011, D-012, D-025, D-034
- 설계 시점: 3단계
- 작성일: 2026-10-25
- 최종 수정일: 2026-11-15 (묶음 9 구현 반영, D-034)

> 요구사항 7절(공동 편집 모델)과 D-011을 구현 수준으로 구체화한 초안이다. 2026-10-18에 이 개발 환경에서 확인한 사실(GitHub API와 raw 주소의 교차 출처 허용, OAuth 토큰 교환 불가)을 전제로 한다.

## 1. 목적

- 여행 데이터를 여행 저장소(GitHub, 여행마다 하나)에 Key로 암호화해 저장하고, 앱을 열 때 최신 버전을 자동으로 읽어 보인다(R-21, R-25). 역할(메인·서브·공유자)에 따라 동작을 제한하고(R-22), 서브의 제안을 본문과 분리해 저장한 뒤 메인의 승인으로 반영한다(R-23). 저장 시 버전 충돌을 감지해 경고한다(R-24). 파일 내보내기와 가져오기를 제공한다(R-09).
- 경계: 여행 데이터의 내용(일정, 선택, 비용)은 다른 엔진과 화면이 만든다. E7은 저장·읽기·버전·암호화·역할·제안 기록만 맡는다. 기준 데이터(E1 산출물)는 앱 저장소의 정적 파일이며 E7의 대상이 아니다.

## 2. 입력

| 입력 | 출처 | 필수 |
|---|---|---|
| 여행 저장소 주소(소유자/저장소), Key(비밀 문구) | 사용자 설정. 공유자는 이 둘만 | 필수 |
| 개인 접근 토큰(해당 저장소 하나, 콘텐츠 쓰기 권한, 만료 설정) | 메인·서브 수립자 설정 | 수립자만 |
| 여행 데이터 개체(Trip, Selection, Day/Item, Lodging, CostEstimate, Export 기록) | 화면, E2·E4·E6 결과 | 필수 |
| 제안(대상 항목, 변경 내용, 메모) | 서브 수립자 화면 | 선택 |
| 사용자 동작: 저장, 새로 고침, 제안 작성·승인·거절, 내보내기, 가져오기 | 화면 | |

## 3. 출력

| 출력 | 내용 |
|---|---|
| 저장소 파일 | `trip.json.enc`(본문: roles{main, sub[]}, plan, applied[반영한 제안 ID], updated), `proposals/<시각>-<작성자>.json.enc`(제안 하나당 파일: id, author, created, kind, target, value, memo, status, decided, base), `meta.json`(평문: 형식 버전, 암호화 매개값 salt·반복수. 개인 정보 없음) |
| 커밋 | 저장마다 커밋 하나. 커밋 SHA가 동기화 버전. 메시지는 "저장: <요약>" 또는 "제안/승인/거절: <id>" |
| 로컬 상태 | Key, 토큰, 마지막으로 읽은 버전 SHA와 저장 안 된 변경 여부, meta.json 사본, 저장 전 작성 중인 내용(draft), 충돌 때 보존한 내 변경. 그 외는 기기에 두지 않는다(D-011) |
| 화면 상태 | 현재 버전(짧은 SHA, 커밋 시각, 작성자), 최신 여부, 충돌 경고, 제안 목록과 상태, 역할 |
| 내보내기 파일 | `trip-<날짜>.json` 평문(결정 필요). 가져오기는 같은 형식 |

## 4. 규칙과 알고리즘

1. 암호화(R-25): 브라우저 WebCrypto. 키 유도 PBKDF2-SHA-256(반복수 결정 필요, 제안 600,000회), 암호화 AES-GCM 256, 파일마다 무작위 IV 12바이트. 파일 형식은 {v, salt, iv, data} base64. salt는 여행 저장소 생성 때 한 번 만들어 meta.json에 둔다. Key 최소 길이는 결정 필요(제안 12자, 공백 허용). Key는 링크나 저장소에 절대 넣지 않는다.
2. 역할 판정(R-22, 구현 세부는 D-034): 목록에 없는 계정과 계정을 확인하지 못한 토큰은 공유자로 본다. 메인이 비어 있는 예전 저장소는 토큰을 가진 계정이 메인이다. 서브 목록은 메인이 설정 화면에서 관리한다. 판정과 권한표는 app/src/engines/e7/roles.js. Key만 있으면 공유자. 토큰이 있으면 `GET /user`로 계정을 확인하고 본문의 roles 목록과 대조해 메인 또는 서브. 첫 저장(저장소 초기화)을 한 계정이 메인으로 기록된다. 역할 목록은 본문 안에 암호화해 둔다(결정 필요: 평문 meta.json에 두면 계정명이 노출되므로 암호화를 제안). 서브의 본문 쓰기는 앱이 막는다. GitHub 토큰은 파일 단위 권한이 없어 기술적으로는 가능하므로 리스크로 기록한다.
3. 읽기(R-21, 구현 세부는 D-034): 저장소와 Key가 기기에 있으면 앱을 열 때 자동으로 읽는다. 저장 안 된 내 변경이 있으면 본문을 덮어쓰지 않고 기준 버전만 맞춘다. 화면 복귀 때 최신이 아니면 내 변경이 없을 때 바로 다시 읽고, 있으면 "오래됨"으로 표시한다. 호출 수는 첫 연결 3회(최신 커밋, meta.json, 본문), 다음부터 2회(meta.json은 기기에 보관). 모든 읽기는 브라우저 캐시를 그대로 쓰지 않고 최신 여부를 확인한다(GitHub 응답의 60초 캐시 때문). 앱을 열 때와 화면 복귀 때 `GET /repos/{o}/{r}/commits?path=trip.json.enc&per_page=1`로 최신 커밋 SHA를 얻고, 로컬 SHA와 다르면 `GET /repos/{o}/{r}/contents/trip.json.enc?ref=<sha>`로 받아 복호화한다. raw 주소는 5분 캐시가 있어 최신 확인에는 쓰지 않는다. 공유자는 로그인 없이 읽는다(공개 저장소). 비인증 API 한도는 IP당 시간 60회이므로 한 번 열 때 호출 2회로 제한한다.
4. 쓰기: `PUT /repos/{o}/{r}/contents/<경로>`에 base64 내용과 현재 파일 SHA를 보낸다. GitHub가 SHA 불일치 시 409를 돌려주므로 이것을 충돌 감지의 1차 수단으로 쓴다. 올리기 전에 내용을 UTF-8 바이트로 바꿔 32,768바이트씩 base64로 만든다(한 번에 바꾸면 브라우저 엔진의 함수 인자 수 한도에 걸린다). 파일이 838,860바이트(GitHub 읽기 API가 본문을 함께 주는 1MB의 80%)를 넘으면 호출하지 않고 "파일이 너무 큽니다"로 알린다(D-042).
5. 충돌 처리(R-24): (a)로 보존한 내 변경은 설정 화면에서 다시 적용하거나 버린다(다시 적용한 뒤 저장해야 저장소에 반영된다). 저장 직전 3항으로 최신 SHA를 확인하고, 기준 SHA와 다르거나 PUT이 409면 경고한다. 선택지(결정 필요, 1차 제안): (a) 최신 버전을 불러오고 내 변경은 draft로 보존, (b) 내 변경으로 덮어쓰기(두 번 확인). 항목 단위 병합은 2차.
6. 제안과 승인(R-23, 구현 세부는 D-034): 종류는 add(추가, 날짜 선택 가능), remove(삭제), move(날짜 이동, 미배치 포함), dwell(체류 시간 15~600분), memo(500자 이내)다. 서브가 장소 선택·날짜·체류 시간을 바꾸는 동작은 제안 보내기 시트로 바뀌고, 그 밖의 편집 요소는 서브에게 보이지 않는다. 승인은 (1) 본문에 적용(app/src/engines/e7/proposals.js의 applyProposal)해 저장하고 반영한 ID를 applied에 적은 뒤 (2) 제안 상태를 바꾼다. (1)이 충돌하면 기기의 계획도 바뀌지 않는다. applied에 이미 있는 제안은 상태만 바꾼다. 적용할 수 없는 제안은 승인되지 않는다. 승인된 메모는 plan.notes에 남는다. 목록 읽기는 디렉터리 1회 + 새로 생겼거나 바뀐 파일마다 1회다. 서브는 자기 제안만, 메인은 전체를 본다. 서브는 `proposals/` 아래 새 파일만 만든다(본문 불변). 제안 내용은 대상(날짜·항목 ID), 변경 종류(추가·삭제·이동·체류 시간·메모), 값, 메모, 상태(대기). 메인은 제안을 열어 승인하면 본문에 반영한 커밋과 제안 상태를 승인으로 바꾼 커밋을 차례로 만든다. 거절도 상태만 바꾼다. 제안 파일은 삭제하지 않는다.
7. 자동 저장: 수립자의 편집은 로컬 draft에 즉시 저장하고, 사용자가 "저장"을 누르거나 2분 유휴(결정 필요) 뒤 커밋한다. 저장 실패(네트워크, 토큰 만료)는 draft를 유지하고 경고한다.
8. 내보내기·가져오기(R-09): 본문을 평문 JSON으로 내려받는다(사용자 기기에서 보관). 가져오기는 파일을 읽어 draft에 올리고 사용자가 저장하면 커밋한다. 내보낸 파일을 가져오면 같은 계획이 복원되어야 한다(해시 동일).
9. 공유: 링크의 `?repo=`를 앱이 읽어 저장소 주소를 채우고 Key 입력을 안내한다. 기기에 다른 여행의 설정이 있으면 그 Key와 토큰은 쓰지 않는다. 공유자에게는 앱 주소에 저장소 주소를 붙인 링크를 보내고 Key는 따로 전달한다. Key를 링크에 넣는 옵션은 두지 않는다(결정 필요).
10. 저장소 초기화: 메인이 GitHub에서 공개 저장소를 만들고(사용자 행동), 앱의 설정 화면에서 주소·Key·토큰을 입력하면 앱이 meta.json과 빈 본문을 첫 커밋한다. 서브는 메인이 GitHub에서 공동 작업자로 추가한다(사용자 행동).

## 6. 품질 기준과 평가 방법

| 기준 | 목표 | 측정 |
|---|---|---|
| 암호화 | Key 없이 저장소 파일을 열면 내용을 읽을 수 없음 | 복호화 실패 테스트, 평문 문자열 검색 0건 |

| 역할 제한 | 공유자의 쓰기 호출 0건, 서브의 본문 쓰기 0건 | scripts/collab_check.py의 역할별 PUT 집계 |
| 자동 읽기 | 공유자가 앱을 열면 최신 버전이 3초 안(추정)에 표시되고 버전이 보임 | 기기 측정 |
| 내보내기 | 내보내기→가져오기 결과가 원본과 동일 | 해시 비교 |
| 로컬 저장 | Key, 토큰, draft 외 데이터가 기기에 남지 않음 | 저장소 검사 |

## 8. 관련 결정

- D-011 GitHub 여행별 저장소, 공개 저장소 + Key 암호화, 로컬 최소 저장, 토큰 입력 방식. D-012 엔진 분리.
- D-025(2026-10-25 설계 동의)로 제안값 확정: (a) Key 최소 길이 12자와 PBKDF2 반복수 600,000, (b) 역할 목록을 본문 안에 암호화, (c) 충돌 처리 1차는 불러오기·덮어쓰기 두 선택지, (d) 토큰 만료 권고 90일, (e) 내보내기 파일은 평문, (f) 공유 링크에 Key 미포함, (g) 자동 저장 유휴 2분.

## 10. 알려진 한계 (2026-11-15)

- 업로드 인코딩(2026-11-16 해소, T-051·D-042): 한 번에 base64로 바꾸던 코드가 큰 파일에서 실패했다(실측: 크롬 124,745바이트·Node 125,310바이트까지 성공, 문서 기준 사파리는 인자 65,536개). 조각 단위 변환으로 바꿔 이 한도는 없어졌고, 남은 기준은 GitHub의 1MB다. 여유 20%를 두어 838,860바이트를 넘는 파일은 올리지 않는다. 올리는 파일은 장소 32곳·10일에 약 25KB, 장소 하나에 약 0.7KB였다(실측). 사파리에서의 실제 변환은 확인하지 못했다(미확인).
- 서브의 토큰은 기술적으로 본문 파일도 쓸 수 있다(GitHub 토큰에 파일 단위 권한이 없다). 앱이 막을 뿐이다(4절 2항의 리스크).

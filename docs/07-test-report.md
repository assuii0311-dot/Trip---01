## 7. 배포 절차

배포는 main 브랜치에 푸시되면 GitHub Pages 워크플로가 자동으로 한다. 작업은 작업 브랜치에서 하고 PR로 main에 넣는다.

1. **테스트**: 바뀐 영역의 테스트를 실행한다.
   - 앱: `node --test tests/app/*.test.js`
   - 파이프라인: `<venv>/bin/python -I -m pytest pipeline/tests` (가상환경은 저장소 밖에 두고 `pipeline/requirements.txt`로 설치)
2. **로컬 점검**: 사이트를 만들어 브라우저 점검을 돌린다.
   - `bash scripts/stage.sh <디렉터리>` (`app/`과 `data/`를 한 디렉터리에 모은다)
   - `python3 -m http.server 8765 -d <디렉터리>`
   - `<venv>/bin/python -I scripts/flow_check.py http://127.0.0.1:8765/ <스크린샷 디렉터리>` (다른 스크립트도 같은 방식. 가상환경에 `playwright` 파이썬 패키지가 필요하다)
3. **커밋과 푸시**: 검증이 끝난 작업 단위를 작업 브랜치에 커밋하고 푸시한다. 경로를 지정해 추가한다.
4. **PR**: 사용자가 요청하면 main을 대상으로 PR을 만든다. 본문에 요약, 검증, 검증하지 못한 것을 적는다.
5. **병합**: 사용자가 요청하면 병합 커밋 방식으로 병합한다. 히스토리를 바꾸는 방식(rebase, squash)은 쓰지 않는다.
6. **배포 실행 확인**: 워크플로 `pages`가 테스트 → 사이트 구성(`scripts/stage.sh site`) → 올리기 → 배포를 차례로 한다. 저장소의 Actions에서 실행이 `success`인지, 커밋이 병합 커밋인지 확인한다.
7. **배포본 점검**: 배포 주소에서 `flow_check.py`를 다시 돌려 단계 수와 콘솔 오류 0건을 확인한다. 이 개발 환경에서는 브라우저에 프록시를 지정해야 배포 주소에 닿는다.
8. **작업 브랜치 맞추기**: `git fetch origin main && git merge --ff-only origin/main` 뒤 푸시한다.
9. **기기 확인 요청**: 확인할 항목을 목록으로 사용자에게 전달한다. 설치한 앱에 예전 화면이 보이면 새로고침한다.

되돌릴 때는 문제가 된 변경을 되돌리는 커밋을 만들어 같은 절차로 배포한다. 강제 푸시와 히스토리 변경은 하지 않는다(CLAUDE.md 규칙 7).

# 1단계 요구사항 정의서

- 작성일: 2026-10-18
- 상태: 1차 확정. 2026-10-18 사용자 수정 요청 반영(D-015). 2단계 데이터 정의 결과에 따라 입력 항목과 조건부 기능을 재조정한다.
- 관련 결정: D-001, D-002, D-010, D-011, D-012, D-013, D-014, D-015, D-016, D-017
- 완료 기준: 기능 목록에 우선순위가 매겨져 있고(5절), 범위 밖 항목이 명시되어 있다(14절).

## 1. 문제와 목적

### 해결하려는 문제

1. 개인의 취향을 반영하지 못하는 패키지 형태의 여행 계획
2. 여행지에 대한 배경지식 없이는 계획과 판단이 불가능한 구조
3. 한국인 중심의 획일적이고 제한적인 여행 계획. 현지인 또는 글로벌 중심의 정보와 선호를 바탕으로 구성한다.
4. 여행 기록이 자동으로 남지 않아 추억을 관리하기 어려운 점. 이 항목은 별도 프로젝트로 분리한다(14절).

### 목적

- 공개 서비스를 지향한다.
- 제약이 크면 단계적으로 적용한다. 본인용 도구 또는 지인 공유용으로 먼저 검증한 뒤 공개 범위를 결정한다.

## 2. 대상 사용자와 역할

| 역할 | 인원 | 권한 |
|---|---|---|
| 메인 계획 수립자 | 1명 | 계획 본문 편집, 제안 승인 |
| 서브 계획 수립자 | 0~2명 | 계획 열람, 제안(메모) 작성 |
| 공유자 | 다수(여행 참여자) | 계획 열람 |
| 기록 이용자 | 다수 | 후속 범위. 개별 기록 작성과 읽기 전용 공유 |

- 동행 여행이 많고, 계획을 세우는 사람은 소수(1~3명), 계획을 보는 사람은 다수다.

## 3. 여행 유형과 지역

- 지역: 해외 중심. 1차 스페인, 2차 일본(도쿄). 국내는 해외 이후.
- 기간: 해당 국가에 적합한 일정. 유럽 1~2주, 일본 3~5일.
- 유형: 자유여행. 다양한 취향을 반영할 수 있도록 여행 카테고리는 가능한 한 다양하게 둔다.

## 4. 핵심 사용 흐름

계획은 다음 여섯 단계로 만들어진다. 각 단계는 5절의 요구사항과 6절의 엔진에 대응한다.

| 흐름 | 내용 | 요구사항 | 엔진 |
|---|---|---|---|
| 1 | 사용자 기본 정보 입력. 여행 기본 정보, 여행 형태, 취향 | R-01, R-02, R-03 | E1, E2(취향 선택지) |
| 2 | 해당 지역에 대한 요약 추천과 사용자 선호 분석 | R-05 | E2 |
| 3 | 2단계 데이터 기반 1차 추천. 모든 데이터 노출과 세 수준의 대안 포함 | R-04, R-06 | E1, E2 |
| 4 | 1차 추천을 포함해 이용자가 선택 | R-07, R-08 | 없음 |
| 5 | 일정 생성. 여행 기간 내 불가해도 초과분을 표시해 제공 | R-14 | E4 |
| 6 | 수정과 일정 재생성. 수정 범위(장소, 소요 시간, 방문 순서 등) 선택 | R-15 | E4 |

## 5. 기능 요구사항

표기: 각 요구사항은 번호, 요구, 충족 조건, 데이터 의존, 담당 엔진을 갖는다. 우선순위는 11월 스페인 계획 완료 목표 기준이다. 선택지, 화면, 세부 규칙은 3단계 기획과 엔진 설계 문서에서 정한다.

### 우선순위 1. 입력

입력 항목은 여기서 1차 구성하고, 2단계에서 추출되는 데이터 기준으로 재구성한다.

- **R-01 여행 기본 정보 입력**
  - 요구: 여행 기간, 여행 도시, 출발과 도착 공항, 출발과 도착 시각, 인원을 입력한다.
  - 충족 조건: 입력값이 저장되고 일정표의 시작과 끝 기준, 그리고 후보 수집(R-04)의 범위로 쓰인다.
  - 데이터 의존: 없음. 엔진: 없음.
- **R-02 여행 형태 입력**
  - 요구: 예산 수준, 하루 일정의 시작 시간과 마감 시간, 식사 형태(반주, 가볍게, 간식 포함 등)를 입력한다.
  - 충족 조건: 입력값이 저장되고 추천(E2)과 일정 생성(E4)의 입력으로 쓰인다.
  - 데이터 의존: 없음. 엔진: 없음.
  - 비고: 항목(예산 수준, 시작과 마감 시간, 식사 형태)은 가안이다. 확정하지 않고 2단계 데이터를 보고 분류를 정한다.
- **R-03 취향 입력**
  - 요구: 여행 카테고리에 대한 선호를 선택한다. 선택지는 2단계에서 수집한 데이터의 분류를 기반으로 제공한다.
  - 충족 조건: 데이터 기반 선택지가 제시되고, 선택값이 저장되어 추천(E2)의 입력으로 쓰인다.
  - 데이터 의존: 있음. 카테고리 체계는 2단계 데이터에서 도출한다. 엔진: E1(분류 체계), E2(선호 분석).

### 우선순위 2. 후보 수집과 추천

- **R-04 후보 수집과 제공**
  - 요구: 스페인의 도시, 지역, 장소를 계층으로 가능한 한 최대로 수집해 제공한다. 사용자는 추천 여부와 무관하게 모든 후보를 열람할 수 있다. 데이터 원천은 여러 출처를 교차검증해 구성한다.
  - 충족 조건: 도시에서 지역, 지역에서 장소로 내려가며 탐색할 수 있고, 수집된 전체 후보가 노출된다. 후보마다 교차검증 결과(일치, 불일치, 단일 출처)가 기록된다.
  - 데이터 의존: 있음. 다중 출처 교차검증(P-14). 2단계 확인. 엔진: E1.
- **R-05 지역 요약 추천과 선호 분석**
  - 요구: 도시와 지역에 대한 요약 추천을 제공하고, 입력된 여행 형태와 취향을 분석해 사용자 선호를 정리한다.
  - 충족 조건: 도시와 지역마다 요약이 표시되고, 사용자 선호 분석 결과가 표시된다.
  - 데이터 의존: 있음. 엔진: E2.
- **R-06 기준 기반 1차 추천**
  - 요구: 사용자의 선택과 데이터 기반 기준을 결합한 기준으로 후보 중 추천을 표출한다. 추천은 하나의 안이 아니라 대안을 포함하며, 대안은 세 수준으로 제공한다. 전체 일정 기준 대안, 도시 기준 대안, 가장 하위 단위(장소) 기준 대안. 추천 근거를 함께 표시한다.
  - 충족 조건: 추천 목록과 근거가 표시되고, 세 수준의 대안이 제공되며, 추천되지 않은 후보도 열람할 수 있다.
  - 데이터 의존: 있음. 엔진: E2.

### 우선순위 3. 선택, 배치, 저장

- **R-07 이용자 선택**
  - 요구: 1차 추천을 포함한 후보에서 장소를 선택하고, 후보에 없는 장소를 직접 추가한다.
  - 충족 조건: 선택 목록이 저장된다.
  - 데이터 의존: 없음. 엔진: 없음.
- **R-08 일정표 배치와 지도 표시**
  - 요구: 선택한 장소를 날짜별 일정표에 배치하고 지도에 표시한다.
  - 충족 조건: 날짜별 목록과 지도 위 위치가 일치한다.
  - 데이터 의존: 지도 타일. 엔진: 없음.
- **R-09 저장과 내보내기**
  - 요구: 계획을 저장하고 파일로 내보내거나 가져온다.
  - 충족 조건: 내보낸 파일을 가져오면 같은 계획이 복원된다.
  - 데이터 의존: 없음. 엔진: E7(저장 위치는 9절).

### 우선순위 4. 숙박

- **R-10 숙박 도시와 지역 추천**
  - 요구: 일정에 따라 도시별 숙박 일수와 숙박 지역을 추천한다.
  - 충족 조건: 11월 숙소 예약에 쓸 수 있는 수준으로 도시, 지역, 일수가 제안된다.
  - 데이터 의존: 있음. 2단계 확인. 엔진: E2.

### 우선순위 5. 이동

- **R-11 이동 경로와 소요 시간**
  - 요구: 장소 사이의 이동 수단별 경로와 소요 시간을 제공한다. 이동 수단은 버스, 지하철, 택시, 기차, 비행기, 배 등 모든 수단을 포함한다. 최적안과 대안을 함께 표시한다. 필수 기능이며 8절의 대안 사다리와 수단별 데이터 표를 적용한다.
  - 충족 조건: 일정표의 연속한 두 장소 사이에 최적 이동안과 대안이 소요 시간과 함께 표시된다.
  - 데이터 의존: 있음. 2단계 확인. 엔진: E3.
- **R-12 대중교통 상세**
  - 요구: 대중교통 이동의 노선, 환승, 소요 시간을 제공한다. 필수 기능이며 8절의 대안 사다리를 적용한다. 실패 시 대안은 재논의한다.
  - 충족 조건: 사다리 중 확정된 단계의 내용이 표시된다.
  - 데이터 의존: 있음. 2단계 확인. 엔진: E3.
- **R-13 실시간 운행 정보 링크**
  - 요구: 출발지와 도착지를 담은 구글맵 경로 링크를 제공한다(D-013).
  - 충족 조건: 링크를 열면 해당 구간의 대중교통 경로가 구글맵에서 열린다.
  - 데이터 의존: 없음. 엔진: E3.

### 우선순위 6. 일정 생성

- **R-14 일정 생성**
  - 요구: 선택한 장소, 이동 시간, 영업시간, 여행 형태(R-02)를 입력으로 날짜별 일정을 생성한다. 여행 기간 안에 넣을 수 없는 장소도 초과분으로 표시해 제공한다.
  - 충족 조건: 생성된 일정이 하루 시작과 마감 시간 안에 들어가고, 초과분이 구분되어 표시된다.
  - 데이터 의존: R-11, R-12에 의존. 엔진: E4.
- **R-15 수정과 재생성**
  - 요구: 수정 범위(장소, 소요 시간, 방문 순서 등)를 선택해 일정을 수정하고 재생성한다.
  - 충족 조건: 선택한 범위만 바뀌고 나머지는 유지된다.
  - 데이터 의존: 없음. 엔진: E4.

### 우선순위 7. 장소 설명

- **R-16 장소 설명 글**
  - 요구: 선택한 장소마다 요약 설명과 상세 설명을 제공한다. 여행 중 현장에서 읽어 장소 정보를 파악하는 용도다. 출처를 표기한다.
  - 충족 조건: 일정에 포함된 모든 장소에 요약과 상세가 있고 출처가 표시된다.
  - 데이터 의존: 출처 텍스트. 영문 Wikivoyage와 위키백과를 기본으로 하되, 교차 검증이 가능한 더 넓은 범위(Wikidata 설명, OpenStreetMap 태그, 공공 관광 자료 등)를 2단계에서 검토한다(P-08). 라이선스 확인이 필수다. 엔진: E5. 생성은 개발 시점에 하며 절차는 6절 E5 참조.
- **R-17 장소 설명 음성**
  - 요구: 설명을 음성으로 들을 수 있다.
  - 충족 조건: 브라우저 내장 음성 합성으로 한국어 읽기가 동작한다.
  - 데이터 의존: 없음. 엔진: 없음.

### 우선순위 8. 예약

- **R-18 예약 필요 여부 제안**
  - 요구: 장소마다 예약 필요 여부를 제안한다. 판단 기준은 클로드가 제안하고 사용자가 확정한다. 쓸 수 있는 데이터는 2단계에서 확인한다.
  - 충족 조건: 일정의 각 장소에 예약 필요 여부와 근거가 표시된다.
  - 데이터 의존: 있음. 미확인. 엔진: E2.
- **R-19 예약 정보 입력**
  - 요구: 장소와 숙소에 예약 정보를 입력하고 일정에서 확인한다.
  - 충족 조건: 입력한 예약 정보가 해당 일정 항목에 표시된다.
  - 데이터 의존: 없음. 엔진: 없음.

### 우선순위 9. 명칭

- **R-20 명칭 병기**
  - 요구: 기본 언어는 한국어다. 현지에서 확인이나 검색이 필요한 장소는 스페인어와 영어 공식 명칭(구글맵에서 검색되는 명칭)을 병기하고 좌표 기반 구글맵 검색 링크를 붙인다. 병기 대상의 기준은 기획에서 정한다.
  - 충족 조건: 병기 대상 장소에 현지어와 영어 명칭과 링크가 표시된다.
  - 데이터 의존: Wikidata, OpenStreetMap 명칭. 엔진: E1.

### 우선순위 10. 동행자 공동 편집

- **R-21 Key 동기화**
  - 요구: 여행 저장소 주소와 Key를 설정하면 앱을 열 때 최신 버전을 자동으로 읽어 표시한다. 현재 버전을 표시한다.
  - 충족 조건: 공유자는 설정 후 추가 행동 없이 최신 계획을 본다.
  - 데이터 의존: 없음. 엔진: E7.
- **R-22 역할 구분**
  - 요구: 메인 수립자는 본문을 편집한다. 서브 수립자는 제안을 위해 계획과 후보 리스트 전체를 열람하고 제안을 작성한다. 공유자는 계획을 열람만 한다.
  - 충족 조건: 역할에 없는 동작은 할 수 없다.
  - 데이터 의존: 없음. 엔진: E7.
- **R-23 제안과 승인**
  - 요구: 서브 수립자의 제안은 본문과 분리된 기록으로 저장되고, 메인 수립자가 승인하면 본문에 반영된다.
  - 충족 조건: 승인 전 제안은 본문을 바꾸지 않는다.
  - 데이터 의존: 없음. 엔진: E7.
- **R-24 버전 충돌 처리**
  - 요구: 저장 시 기준 버전이 최신 버전과 다르면 경고하고 처리 방법을 선택하게 한다.
  - 충족 조건: 경고 없이 최신 버전이 덮어써지는 경우가 없다.
  - 데이터 의존: 없음. 엔진: E7.
- **R-25 암호화 저장**
  - 요구: 공개 저장소에 저장되는 계획 데이터는 Key로 암호화한다.
  - 충족 조건: Key 없이 저장소 파일을 열면 내용을 읽을 수 없다.
  - 데이터 의존: 없음. 엔진: E7.

### 우선순위 11. 비용

- **R-26 예상 비용**
  - 요구: 입장료, 식비, 교통비, 숙박비를 데이터 기반으로 추정한다. 사용자 입력 기반 추정은 하지 않는다. 2단계 PoC에서 네 항목을 모두 시도하고 결과를 분류한 뒤 방향을 재결정한다(8절).
  - 충족 조건: 재결정으로 확정된 항목의 추정치가 일정에 표시된다.
  - 데이터 의존: 있음. 2단계 확인. 엔진: E6.

### 우선순위 12. 구글맵 일괄 저장

- **R-27 장소 일괄 구글맵 저장**
  - 요구: 일정 또는 후보의 장소들을 한 번에 구글맵에서 쓸 수 있게 제공한다. 두 형태로 한다. 첫째, 장소 목록을 KML 또는 CSV 파일로 내보내 사용자가 Google My Maps에 한 번 가져오기 한다. 둘째, 하루 일정의 장소를 경유지로 담은 구글맵 경로 링크를 제공한다.
  - 충족 조건: 내보낸 파일을 My Maps에 가져오면 장소가 모두 표시되고, 경로 링크를 열면 하루 일정의 경유지가 구글맵에 표시된다.
  - 데이터 의존: 없음. 장소 좌표와 명칭은 R-04, R-20에서 확보한다. 엔진: 없음.
  - 사실: 구글은 사용자의 저장 목록에 장소를 추가하는 공개 API를 제공하지 않는다. Google My Maps는 무료이며 KML과 CSV 가져오기를 지원한다. 경로 링크의 경유지 수 제한은 미확인이다(P-16).

### 후속 범위

일본(도쿄) 데이터, 수동 여행 기록과 읽기 전용 공유, 준비물 체크리스트, 오프라인 열람, UI 다국어. 2차 반복에서 다룬다.

### 범위 밖

자동 여행 기록(위치 추적 기반). 별도 프로젝트로 후속 진행한다.

## 7. 공동 편집 모델

D-011에 따른다.

- 구조: 앱 저장소 하나(GitHub Pages로 앱 제공)와 여행마다 하나의 여행 저장소(계획 데이터와 제안 기록). 앱의 동기화 설정은 여행 저장소 주소와 Key다.
- 버전: 모든 저장은 커밋이며 커밋이 동기화 버전이다. 앱은 읽은 커밋을 기억하고 열 때마다 최신과 비교한다.
- 읽기: 공개 저장소를 로그인 없이 읽는다. 공유자는 Key를 한 번 입력한 뒤 추가 행동이 없다.
- 쓰기: 메인과 서브 수립자는 GitHub 계정으로 여행 저장소의 공동 작업자가 되고, 그 저장소 하나와 파일 쓰기 권한으로 범위를 좁힌 개인 접근 토큰을 발급해 앱에 한 번 입력한다. 이후 저장은 자동으로 커밋된다.
- 제안과 승인: 서브 수립자의 제안은 별도 파일로 저장되어 본문과 충돌하지 않는다. 메인 수립자가 승인하면 본문에 반영된다.
- 암호화: 저장소에는 Key로 암호화된 파일만 올라간다. 브라우저 내장 암호화 기능을 쓴다.
- 로컬 저장: Key, 토큰, 저장 전 작성 중인 내용만 기기에 둔다. 계획 데이터는 항상 저장소에서 읽는다.
- 사실(2026-10-18 이 개발 환경에서 확인): GitHub API와 raw 파일 주소는 브라우저 교차 출처 요청을 허용한다. raw 주소는 5분 캐시가 있어 최신 버전 확인은 API로 한다. GitHub OAuth 토큰 교환 주소는 브라우저 요청을 허용하지 않아 로그인 방식은 쓸 수 없다.
- 리스크: 기기에 저장된 토큰이 탈취되면 해당 여행 저장소에 쓰기가 가능하다. 저장소 범위 제한과 만료 설정으로 피해를 한정한다. GitHub를 소규모 개인 데이터 저장에 쓰는 것은 문제가 없다고 추정하지만 공개 서비스 단계에서 재검토한다.

## 9. 비기능 요구사항

- 저장 위치: 계획 데이터는 여행 저장소. 로컬 저장은 7절의 최소 범위.
- 비용: 서버 비용 0. 한도가 있는 무료 플랜 서비스는 쓰지 않는다. 유료 데이터는 쓰지 않는다(D-001).
- 언어: UI는 한국어. 명칭 병기는 R-20. UI 다국어는 후속.
- 오프라인 열람: 후속. 있으면 좋음 수준.
- 음성: 브라우저 내장 음성 합성.
- 보안: 토큰은 저장소 범위 제한과 만료 설정. 계획 데이터는 암호화 저장.
- 플랫폼 제약(사실, 5단계에서 결정): 주 사용 기기는 iOS와 Android 모두. 웹으로 만들어도 된다. 개발은 아이패드에서 한다. iOS 네이티브 빌드 도구와 Android Studio는 아이패드에서 실행되지 않는다.

## 10. 제약

- 유료 데이터 미사용(D-001). 무료 티어만 있는 유료 데이터 서비스도 제외.
- 서버 비용 비허용. 향후 가능성은 염두에 두고 검토.
- 개발 환경: 클로드 코드 웹 세션. 아이패드에서 사용.
- 이 개발 환경의 데이터 소스 접속 확인 결과(2026-10-18, 사실)
  - 접속됨: Wikivoyage API, Wikidata SPARQL, 한국어 위키백과 API, Wikimedia 덤프, OSRM 공개 서버, Transitous API, OpenRouteService, Nominatim, planet.openstreetmap.org, bbbike OSM 추출본, OSM 지도 타일, Renfe 공개 데이터, 스페인 교통 데이터 포털, 구글맵 링크, GitHub API와 raw와 Pages
  - 차단됨: Geofabrik, Overpass API 본 서버와 lz4 미러. OSM 데이터 수집은 대체 경로가 필요하다.

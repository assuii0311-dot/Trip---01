# 결정 기록

확정된 결정을 기록한다. 기록된 결정은 사용자가 재검토를 요청하지 않는 한 다시 논의하지 않는다.

## 운영 방법

- 번호는 D-001 형식으로 붙이고 재사용하지 않는다.
- 항목은 날짜, 결정, 근거, 대안 네 가지다.
- 결정은 수정하거나 삭제하지 않는다. 바뀌면 새 결정을 추가하고 결정 문구에 대체하는 번호를 적는다. 대체된 결정은 제목 끝에 "(D-0XX로 대체)"를 붙인다.
- 기존 결정의 일부만 바꾸는 경우에는 새 결정에 어느 결정을 보완하는지 명시하고, 기존 결정의 제목 끝에 "(D-0XX로 보완)"을 붙인다. 기존 결정의 본문은 고치지 않는다.
- 과업 리스트와 작업 계획에서는 결정을 번호로 참조한다.

## D-001. 유료 데이터를 사용하지 않는다

- 날짜: 2026-10-17
- 결정: 유료 데이터를 사용하지 않는다. 무료 티어만 제공하는 유료 서비스도 사용량 증가 시 과금되므로 제외한다.
- 근거: 사용자가 개발 계획 수립의 전제로 제시했다. 무료 티어 제외는 클로드가 제안했고 개발 계획 문서와 CLAUDE.md에 포함해 사용자가 동의했다.
- 대안: 무료 티어 범위 안에서 유료 서비스를 사용한다. 사용량 관리 부담과 과금 위험 때문에 채택하지 않았다.

## D-002. 개발 계획을 8단계로 진행한다

- 날짜: 2026-10-17
- 결정: 원안 5단계에 기술 설계, 테스트 및 배포, 운영 및 피드백 반영을 추가해 8단계로 진행한다. 각 단계 산출물은 docs 아래 문서로 남긴다.
- 근거: 일반 모바일 서비스 개발 과정과 비교해 기술 설계, 테스트와 배포, 운영 단계가 빠져 있었다. 클로드를 활용한 개발에서는 산출물이 저장소 파일로 있어야 다음 단계의 참조 자료가 된다. 사용자가 수정안으로 문서 커밋을 요청했다.
- 대안: 원안 5단계(요구사항 정의, 데이터 정의, 기획, UI/UX 디자인, 개발).

## D-003. 업무 규칙을 CLAUDE.md에 기록한다

- 날짜: 2026-10-17
- 결정: 사용자가 제안한 규칙 6개에 커밋과 푸시, 결정 기록, 완료 보고 형식, 언어 규칙 4개를 더해 총 10개 규칙을 CLAUDE.md에 기록한다.
- 근거: 대화에서 정한 규칙은 세션이 끝나면 유지되지 않는다. 저장소 루트의 CLAUDE.md는 세션 시작 시 읽힌다.
- 대안: 대화에서만 규칙을 유지한다. 세션마다 다시 설명해야 하므로 채택하지 않았다.

## D-004. 작업 범위는 클로드가 정의하고 사용자가 확인한다

- 날짜: 2026-10-17
- 결정: 범위를 요청에 명시된 파일과 기능으로 한정하지 않는다. 클로드가 요청에서 포함, 제외, 변경 대상 파일을 정의해 작업 계획에 명시하고, 사용자가 계획 동의로 확인한다.
- 근거: 모든 요청이 파일과 기능을 명시하기는 어렵고, 그 기준은 모든 경우를 포괄하지 못한다는 사용자 지적. 제외 항목을 명시하면 파일을 열거하지 않아도 범위를 확인할 수 있다.
- 대안: 요청에 명시된 파일과 기능으로 한정한다. 포괄성이 부족해 채택하지 않았다.

## D-005. 경미한 작업도 예외 없이 계획을 제시한다

- 날짜: 2026-10-17
- 결정: 오타 수정 같은 경미한 작업에도 예외 없이 작업 계획을 제시하고 동의 후 착수한다.
- 근거: 사용자 피드백 없이 작업이 진행되는 것을 막는 목적에 가장 충실하다. CLAUDE.md 작성 계획의 권장안에 사용자가 동의했다.
- 대안: 1개 파일, 동작 변화 없는 수정은 한 줄 통지 후 진행한다. 왕복이 줄지만 채택하지 않았다.

## D-006. 미커밋 변경 되돌리기는 보고 후 허용한다

- 날짜: 2026-10-17
- 결정: 작업 중 미커밋 변경을 버리고 직전 커밋 상태로 되돌리는 것은 계획 없이 보고 후 할 수 있다.
- 근거: 직전 커밋은 알려진 상태이므로 복귀가 통제 목적에 어긋나지 않는다. CLAUDE.md 작성 계획의 권장안에 사용자가 동의했다.
- 대안: 되돌리기도 계획 제시 후 승인을 받는다.

## D-007. 언어는 한국어, 코드 식별자는 영어로 한다

- 날짜: 2026-10-17
- 결정: 대화, 문서, 커밋 메시지, 코드 주석은 한국어로 쓴다. 변수명, 함수명, 파일명은 영어로 쓴다.
- 근거: 사용자가 한국어로 소통하며, 이미 작성한 문서와 커밋 메시지가 한국어다. CLAUDE.md 작성 계획의 권장안에 사용자가 동의했다.
- 대안: 코드 주석을 영어로 쓴다.

## D-008. 작업 계획 동의 표현은 "진행"으로 한다

- 날짜: 2026-10-17
- 결정: 사용자가 "진행"이라고 명시할 때 계획에 동의한 것으로 본다. 수정 의견이 있으면 계획을 다시 제시한다.
- 근거: 동의 여부의 모호함을 없앤다. CLAUDE.md 작성 계획에 포함되어 사용자가 동의했다.
- 대안: 별도 표현 없이 문맥으로 판단한다.

## D-009. 과업 리스트와 결정 기록은 누적 논의와 동시 과업의 관리를 위해 유지한다

- 날짜: 2026-10-17
- 결정: docs/TASKS.md와 docs/decisions.md는 프로젝트 수행 과정에서 누적되는 결정과 동시에 진행되는 과업이 누락이나 충돌 없이 관리되게 하기 위해 유지한다. 세션 간 유지는 그 수단이지 목적이 아니다.
- 근거: 사용자가 작업 계획의 목적 문구를 교정하면서 제시했다. 이 프로젝트는 일정 이상의 지속적인 논의와 결정이 필요하고, 동시 다발적인 과업이 수행될 수 있다.
- 대안: 세션 간 연속성 확보를 목적으로 둔다. 수단과 목적이 뒤바뀌어 채택하지 않았다.

## D-010. MVP 범위, 우선순위, 핵심 사용 흐름을 확정한다 (D-015로 보완)

- 날짜: 2026-10-18
- 결정: MVP는 계획 수립자가 스페인 여행을 계획하는 데 필요한 기능으로 하고, 우선순위 11개 묶음(입력, 후보 수집과 추천, 선택과 배치와 저장, 숙박, 이동, 일정 생성, 장소 설명, 예약, 명칭, 동행자 공동 편집, 비용)으로 정한다. 핵심 사용 흐름은 지역 요약 추천과 선호 분석, 1차 추천과 전체 데이터 노출, 이용자 선택, 일정 생성과 기간 초과분 표시, 범위 선택 수정과 재생성의 5단계다. 일본 데이터, 수동 여행 기록, 준비물 체크리스트, 오프라인 열람, UI 다국어는 후속 범위다. 자동 여행 기록은 별도 프로젝트로 범위 밖이다. 항공권과 숙소 예약 기능은 범위 논의에서 삭제한다. 상세는 docs/01-requirements.md.
- 근거: 사용자의 요구사항 답변 16개와 피드백 14건. 11월 숙소 예약을 위한 스페인 계획 완료 목표. 사용자가 공유, 자동 생성, 대중교통 상세, 다국어 명칭, 예약 정보를 후속이 아닌 현재 범위로 결정했다.
- 대안: 클로드 1차 제안. 공동 편집, 자동 생성, 대중교통 상세, 다국어를 후속으로 두고 공유는 파일 교환으로 한정하는 안. 사용자가 현재 범위로 올리기로 결정해 채택하지 않았다.

## D-011. 동행자 공동 편집은 Key 동기화와 제안·승인 구조로 하고 저장소는 GitHub 여행별 저장소를 쓴다

- 날짜: 2026-10-18
- 결정: 공동 편집은 Key 동기화, 메인과 서브 수립자 구분, 서브의 제안과 메인의 승인 구조로 한다. 저장소는 여행마다 하나의 GitHub 저장소를 쓰고 앱은 GitHub Pages로 제공한다. 한도가 있는 무료 플랜 서비스는 쓰지 않는다. 쓰기는 해당 저장소 하나와 파일 쓰기 권한으로 범위를 좁힌 개인 접근 토큰으로 한다. 여행 저장소는 공개로 두고 앱이 Key로 암호화해 저장한다. 로컬 저장은 Key, 토큰, 저장 전 작성 중인 내용으로 한정하고 계획 데이터는 항상 저장소에서 읽는다.
- 근거: 사용자가 제시한 세 조건. 수신자의 행동 최소화, 기존 무료 저장소 활용과 한도 있는 무료 플랜 미사용, GitHub 기반 버전 관리. 2026-10-18 이 개발 환경에서 확인한 사실. GitHub API와 raw 주소는 브라우저 교차 출처 요청을 허용하고, OAuth 토큰 교환 주소는 허용하지 않아 토큰 입력 방식만 가능하다. 공개 저장소를 로그인 없이 읽을 수 있어 공유자의 추가 행동이 없다.
- 대안: 요금 청구가 불가능한 무료 플랜 저장소(Firebase Spark 등). 사용자의 한도 있는 무료 플랜 미사용 방침으로 배제. 기기 간 직접 동기화. 동시 접속 필요와 불안정으로 배제. 파일 교환. 수신자 행동 최소화 조건에 미달해 기본 방식으로는 배제하되 R-09의 내보내기로 보조 수단은 유지.

## D-012. 엔진은 별도 설계 문서로 분리해 관리한다

- 날짜: 2026-10-18
- 결정: 별도 설계가 필요한 구성 요소를 엔진으로 식별한다. E1 데이터 수집·정규화, E2 추천, E3 이동 시간, E4 일정 생성, E5 장소 설명 생성, E6 비용 추정, E7 동기화. 엔진마다 docs/engines/ 아래 설계 문서를 두고 절은 목적, 입력, 출력, 규칙과 알고리즘, 데이터 의존, 품질 기준과 평가 방법, 대안 사다리, 관련 결정, 상태로 고정한다. 설계 문서 작성은 규칙 3을 따르고, 구현은 설계 문서 동의 후 착수한다. 설계 변경은 문서를 먼저 고친다. 과업 리스트에 엔진별 과업을 두고, 코드는 엔진별 독립 모듈과 자체 테스트로 분리한다.
- 근거: 사용자 요청. 엔진 성격의 요소는 설계부터 함께 논의하고 별도로 관리한다.
- 대안: 기획 문서와 기술 설계 문서 안에 엔진 내용을 포함한다. 엔진별 추적과 개별 논의가 어려워 채택하지 않았다.

## D-013. 데이터 제약이 있는 기능은 제외하지 않고 대안 사다리로 다루며, 외부 서비스 링크 제공은 유료 데이터 이용이 아니다

- 날짜: 2026-10-18
- 결정: 데이터 제약이 있는 기능은 확보 가능한 데이터 수준에 따른 대안 사다리로 다룬다. 2단계 PoC는 모든 항목을 100퍼센트 시도하고 결과를 추출 가능, 불확실, 추출 불가로 분류한 뒤 방향을 재결정한다. 어느 단계도 불가하면 대안을 재논의한다. 외부 서비스로 이동하는 링크(구글맵 경로 링크 등)를 제공하는 것은 D-001의 유료 데이터 이용에 해당하지 않는다.
- 근거: 사용자 피드백. 대중교통과 비용 추정은 제외로 결론 내릴 수 없고 데이터 수준에 따른 대안이 필요하다. 사실. 구글맵 경로 링크는 API 키 없이 무료로 쓸 수 있고 이 개발 환경에서 접속이 확인되었다.
- 대안: PoC 기준 미달 시 제외. 클로드 1차 제안이었으나 채택하지 않았다.

## D-014. 11월 완료 가능 여부는 2단계 PoC 후 작업 분해로 판단한다

- 날짜: 2026-10-18
- 결정: 11월 완료 가능 여부는 미확정으로 두고, 2단계 PoC가 끝난 뒤 작업 분해를 바탕으로 판단한다(T-009). 2026-10-17에 클로드가 제시한 "어렵다"는 판단은 철회한다.
- 근거: 그 판단은 작업 분해 없는 경험적 추정이었고, 사용자 응답 주기를 하루 1회로 가정한 것이 틀렸다. 재설계 횟수는 PoC 전에는 알 수 없다.
- 대안: 지금 시점에 범위를 축소한다. 근거 없는 판단으로 범위를 줄이는 것이라 채택하지 않았다.

## D-015. D-010 보완. 핵심 사용 흐름을 6단계로 하고 우선순위 12 구글맵 일괄 저장을 추가한다

- 날짜: 2026-10-18
- 결정: 핵심 사용 흐름은 사용자 기본 정보 입력을 1단계로 추가해 6단계로 한다. 우선순위 묶음에 12 "장소 일괄 구글맵 저장"을 추가한다. 형태는 KML 또는 CSV 내보내기와 Google My Maps 가져오기, 그리고 하루 일정 경유지를 담은 구글맵 경로 링크의 두 가지다. 그 외 D-010의 내용은 유지한다. 같은 날 접수된 수정 요청 중 나머지(여행 도시 입력, 여행 형태 항목의 가안 표시, 데이터 기반 취향 선택지, 다중 출처 교차검증, 세 수준의 대안 추천, 모든 이동 수단과 최적안과 대안 표시, 장소 설명 출처 범위 확대, 서브 수립자의 후보 전체 열람)는 D-010 범위 안의 상세 변경으로 요구사항 정의서에만 반영한다.
- 근거: 사용자 수정 요청(2026-10-18). 사실: 구글은 사용자 저장 목록에 장소를 추가하는 공개 API를 제공하지 않으며, Google My Maps는 KML과 CSV 가져오기를 지원한다.
- 대안: D-010 전체를 대체하는 새 결정을 쓴다. 변경이 일부라 내용 중복이 커서 채택하지 않았다. 이에 따라 운영 방법에 "보완" 표기 규칙을 추가했다.

## D-016. T-006 데이터 정의 PoC의 운영 원칙

- 날짜: 2026-10-19
- 결정: T-006은 A 준비, B 전수 수집, C 교차검증, D 품질 검수, E 이동·비용·링크, F 정리의 여섯 단계로 나누고 단계마다 보고 후 "진행"을 받아 다음 단계를 시작한다. 수집한 원시 데이터는 저장소에 커밋하지 않고 개발 환경에만 두며 스크립트, 요약 수치, 검수 표본만 커밋한다. 품질 검수 표본은 인구와 장소 밀도 기준으로 대도시, 중소 관광 도시, 데이터 빈약 소도시의 세 층으로 나눠 층마다 장소 12곳과 지역 요약 검수용 도시 2곳을 무작위로 뽑는다. 사용자의 여행 계획이나 선호는 표본 선정에 반영하지 않는다. 무료이고 결제 수단이 필요 없는 가입이 필요한 소스는 허용하며 가입은 사용자가 한다. PoC 스크립트는 Python으로 쓰고 가상환경에서 격리 실행한다.
- 근거: 사용자 결정(2026-10-19). 제품의 전제는 배경지식 없는 사용자이므로 표본이 사용자가 아는 지역으로 치우치면 안 된다는 사용자 지적. GitHub의 파일 크기 제한과 원시 데이터의 재생성 가능성.
- 대안: 한 번의 동의로 F까지 진행. 품질 검수와 정리에 사용자 판단이 필요해 채택하지 않았다. 사용자 관심 도시로 표본 선정. 제품 전제에 어긋나 철회했다.

## D-017. 과금 없는 할당량 API는 조건부로 허용하고, YouTube와 Google 검색은 쓰지 않는다

- 날짜: 2026-10-19
- 결정: 과금이 없고 할당량만 있는 무료 API는 그 할당량 안에서 목표한 과업을 달성할 방법이 있을 때만 데이터 소스로 허용한다. YouTube Data API는 개발자 정책의 데이터 집계 금지 조항 때문에 도시나 장소 단위 대리 지표 용도로 쓸 수 없으므로 사용하지 않는다. Google 검색 결과와 Google Trends는 유료 API와 약관 위반 문제로 사용하지 않는다. 사람이 품질 검수 중에 참고하는 용도는 데이터 수집이 아니므로 허용한다.
- 근거: 사용자 결정(2026-10-19)과 조건. 사실: YouTube 개발자 정책의 "Data Aggregation" 조항은 같은 콘텐츠 소유자의 채널 외에는 API 데이터 집계를 금지한다. Custom Search JSON API는 하루 100건 이후 유료다. 상세는 docs/02-data-sources.md 3절.
- 대안: YouTube를 할당량 범위에서 도시 단위로만 쓴다. 정책이 집계 자체를 금지하므로 채택하지 않았다.

## D-018. 품질 검수는 클로드가 구글맵을 소규모 자동 조회해 1차 판정하고 사용자는 모호한 항목만 확인한다

- 대안: 사용자가 전부 직접 검수(약 2시간). 사용자 시간을 줄이기 위해 채택하지 않았다.

## D-020. 현지 관심도 대리 지표(P-17)는 "해외 대표 명소 여부" 신호로 유지하고 요구사항 표현을 재조정한다
